# Práctica, corrección y artefactos

## Flujo conversacional
`prepared → answering → submitted → graded → published`; errores `blocked`/`unpublished` conservan trabajo. Alumno/asignatura/alcance inequívocos antes de preguntar contenido. Alcance por archivo/unidad/concepto/página/encabezado/sección/rango/región verificable, nunca por títulos del plan solamente. Lee solo el alcance y dependencias necesarias; falta de lectura bloquea generación. Carga Skills de formato al leer documentos reales y declara límites reales.

Matriz: alcance → conceptos → preguntas → fuentes/localizadores → clave/rúbrica. La finalidad del examen es comprobar conocimiento del contenido estudiado, no solo resolver unos pocos ítems fáciles. Diseña una muestra amplia, equilibrada y representativa del alcance, con preguntas habituales y exigentes, originales y suficientemente amplias. La cantidad depende de la amplitud y diversidad de conceptos: no uses cinco preguntas ni otro número fijo como evidencia suficiente por defecto. Evita tanto la cobertura superficial como preguntar cada detalle; prioriza conceptos importantes y reparte los ítems entre unidades/conceptos, con solapamiento solo cuando aporte una comprobación distinta. Con perfil respeta patrones observados; la recurrencia histórica orienta pero no predice ni amplía alcance. Sin perfil muestra el aviso general en chat, examen y resultado. Revisa manualmente cobertura, originalidad y adecuación pedagógica; los scripts no generan ni evalúan semánticamente preguntas.

Antes de presentar, estima la cobertura de contenido: conceptos clave dentro del alcance frente a conceptos clave efectivamente evaluados, con vínculo verificable a fuentes/localizadores. Informa qué quedó cubierto y qué quedó fuera o poco muestreado, y expresa el porcentaje solo si el denominador y el método de recuento son explícitos y razonables; de lo contrario, descríbelo cualitativamente. Esta cifra estima representatividad del examen, no porcentaje de conocimiento del alumno, probabilidad de dominio ni confianza estadística. Una buena puntuación en un examen con cobertura estrecha o dificultad baja no permite concluir que el alumno conoce todo el tema/sesión. Si la muestra no permite una comprobación suficientemente amplia, indícalo y ofrece ampliar el examen antes de presentar o después como continuación separada.

Prepara clave y criterios antes de presentar preguntas, con crédito parcial y tratamiento de procedimientos/respuestas abiertas. Consérvalos en contexto interno, separados del examen; no los serialices en archivos visibles antes de entrega. No prometas almacenamiento secreto ni recuperación automática entre chats. Si se pierde contexto, pausa corrección, reconstruye/verifica criterios desde fuentes fijadas y declara límites antes de puntuar; no cambies criterios a posteriori para adaptarlos a respuestas.

Preguntas numeradas, identificadores estables, modalidades `chat`, `paper_image`, `graph_text`, `graph_image`; las dos modalidades de imagen exigen indicarlo explícitamente. Presenta todo en chat; el HTML es estático, accesible y sin formulario, scripts ni recursos externos. Recibe respuestas/adjuntos por ID y permite aclaraciones. No exijas una palabra especial para entregar: un mensaje enviado con respuesta para todas las preguntas es entrega explícita; también una señal `submitted` de la aplicación o una declaración inequívoca de entrega. Si las respuestas llegan fragmentadas y siguen faltando preguntas, continúa sin preguntar si ya terminó; si la entrega está marcada, conserva las ausentes como vacías y corrige según rúbrica. Una respuesta ausente tras entrega puede valer cero según rúbrica; una imagen ilegible o no interpretable NO es respuesta incorrecta: `not_assessable`, puntuación nula, limitación explícita y total inconcluso.

## Datos canónicos locales
`practice-data.json` es un envelope interno `{ exam, submission, result }`; `result` es `null` antes de corregir. No se publica este envelope, porque mezcla información de corrección con enunciado. Sus partes se validan con `assets/exam.schema.json`, `submission.schema.json`, `result.schema.json`; todos los campos declarados son requeridos y las propiedades extra se rechazan.

`exam` contiene identidad, snapshot, plan/perfil, modo, alcance, `source_refs` y `questions: [{ id, prompt, response_mode, requires_image, max_score, source_ref_ids }]`. Es público y nunca contiene clave/rúbrica. `exam.md` incluye `exam-data` JSON con estos datos públicos para verificar el lote sin añadir un archivo remoto `exam.json`. Markdown deriva del modelo; no editar independientemente.

`student: { id, name }`; `subject: { slug, name }`. Snapshot exacto con solo repository/tag. `plan_reference: null | { path, commit, session_ids }`; `profile: null | { path, commit, source_snapshot, references }`. SHA completo de 40 caracteres. `practice_mode` coherente: `general` ↔ perfil nulo, `profile_based` ↔ perfil versionado. Snapshot del perfil idéntico al del examen y plan seleccionado.

`ProfileReference` exacto: `{ id: string, path: string, year: integer|null, read_status: "complete"|"partial", included_locators: string[], excluded_locators: { locator: string, reason: string }[] }`. Conserva igualdad profunda 006→007, sin convertir a fuentes curriculares; si parcial, incluye limitación `partial_profile` en resultado. `SourceRef` curricular: `{ id, path, unit: string|null, key_concepts: string[], locators: [{ kind: "page"|"heading"|"section"|"range"|"region", value }] }`; IDs y localizadores verificables, sin páginas inventadas. No confundir referencias de estilo con temario evaluado.

`submission` contiene identidad, estado `draft`/`submitted`, `submitted_at` con offset o `null`, y todas las respuestas por pregunta: `{ question_id, text: string|null, images: string[] }`. Una respuesta sin contestar conserva ID y texto nulo. Imágenes relativas bajo `submission/`, sin URLs, traversal ni rutas absolutas; nunca `.gitkeep` como respuesta. Los binarios deben existir y ser legibles; el validador confirma persistencia, no interpretación visual.

`result.json` v1.0 autónomo conserva procedencia completa, `created_at`, `corrected_at`, `status`, `score`, resultados por pregunta, áreas de repaso y limitaciones. Cada pregunta: `{ question_id, status, score, max_score, feedback, source_ref_ids, expected_answer, rubric }`; criterio `{ id, description, max_score, awarded_score, feedback }`. Como campos opcionales de compatibilidad, cada pregunta corregida puede añadir `answer_status` (`correct`, `partially_correct`, `incorrect`, `not_assessable`), `strengths: string[]` e `improvement_areas: string[]`. No clasifiques como incorrecta una respuesta correcta que solo puede ampliarse.

Los nuevos resultados publicados DEBEN incluir un `didactic_report` en el mismo `result.json`: metadatos `practice_id`, `student_name`, `subject_name`, `created_at`, `corrected_at`, `status`, `score: { total, max }` y preguntas ordenadas como en el examen. Cada fila incluye `question_id`, `prompt` (copiado del examen), `student_answer` (copiado de la entrega; si hay imagen, indica adjunto sin fingir transcripción), `expected_answer`, `status`, `score`, `max_score`, `feedback`, `strengths` e `improvement_areas`. El script puede derivar el estado histórico ausente del score, pero las nuevas correcciones deben declararlo explícitamente. `result.md` reproduce este contenido para lectura humana. La aplicación sirve un DTO JSON de solo lectura; no procesa `exam.html`.

`score: { total, max, assessed_total, assessed_max }`: máximos de todas las preguntas; agregados assessed solo preguntas completamente evaluadas; total nulo si alguna no es evaluable, `status: inconclusive`, limitación con `prevents_conclusive_grading: true`. Una limitación bloqueante asociada a una pregunta impide marcar esa pregunta como `graded`; si `question_id` es `null`, la limitación se aplica globalmente e impide una corrección concluyente de cualquier pregunta. Feedback, respuesta esperada y rúbrica solo tras entrega. `review_areas: [{ concept, question_ids, recommendation, source_ref_ids }]`; vacío no afirma dominio absoluto. `limitations: [{ code, question_id: string|null, image_path: string|null, description, prevents_conclusive_grading }]` conserva límites de imágenes incluso parciales.

## Herramientas y límites
Python estándar 3.9+, verificado antes de ejecutar; no sustituir runtime por problemas de acceso. Desde esta Skill:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/render_practice.py assets/practice-example.json --output-dir /tmp/practice-unique
python3 scripts/validate_practice.py /tmp/practice-unique
```

`--attachments-dir <root>` opcional exige binarios reales bajo `<root>/submission/...`. El destino debe ser nuevo y su padre existir; colisión no sobrescribe. Para completar un borrador produce un lote local nuevo, verifica identidad y publica actualización autorizada del mismo intento sin borrar archivos ajenos. El renderizador crea staging hermano, valida y renombra solo tras éxito; no permite symlinks en lotes/adjuntos.

`resolve_context` valida recibos locales de lectura, no accede a GitHub ni prueba por sí solo que una lectura sucedió. La conversación debe obtener evidencia real por tag y SHA mediante herramientas disponibles antes de invocarlo. Los schemas son interoperables; `contract.py` implementa solo los keywords incluidos, no validación JSON Schema general. Validación local no prueba permisos ni equivalencia semántica del contenido. No hay frontend/backend/integración web en esta Skill.
